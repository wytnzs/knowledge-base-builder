# 基座契约

> 这个技能交付的不是一堆文件夹，是一层**基座**：结构、规则、协议、体检，外加一条能跑通的工作回路。
> 模块和内容管线长在它上面，读它的接口，不重定义它。
>
> 结构长什么样见 `基础架构.md`；七条固定规则见 `基础架构.md` 第六节，这里不重复。
> 这一页只定**接口**：谁读什么、谁写哪里、怎么插模块、怎么换 Agent、怎么升版本。

## 一、三层

| 层 | 是什么 | 谁负责 | 能不能换 |
|---|---|---|---|
| 基座层 | 六个角色 + 五个根文件 + 读写协议 + 工作回路 + 体检 | 本 skill | 不换；换了就不是同一个库 |
| 模块层 | 收件、铸卡、项目、复盘、体检等日常动作 | `modules/` 八个子 skill | 可增删；按需装 |
| 内容层 | 写作、选题、手册、客户等具体生产管线 | 各自的 skill | 完全自由；只读基座 |

判断：**这件事每周都在做、跟具体内容无关 → 模块；跟某一类产出有关 → 内容层；两者都不该改基座。**

## 二、基座交付物（五个根文件 + 一份采用记录）

| 文件 | 给谁看 | 管什么 | 缺了会怎样 |
|---|---|---|---|
| `README.md` | 人 | 这个库干什么、每个区放什么、怎么用 | 半年后自己忘了怎么用 |
| `AGENTS.md` | 所有 Agent | 规则正文：启动顺序、角色、硬规则、路由、禁止 | 换个会话就要重新交代 |
| `CLAUDE.md` / `AI协作规则.md` | 具体 Agent | 只做入口，指向 `AGENTS.md` | 该 Agent 读不到规则 |
| `.kb-base.json` | 程序 | 角色映射、Agent、版本、契约、已装模块、回路 | 脚本只能猜目录名，升级没法判断 |
| `写入规则.md` | 人和 Agent | 东西从哪进、什么时候建卡、什么不建 | 入口两个月就堵死 |
| `工作回路.md` | 人和 Agent | 用上的路径：触发、读什么、产出什么、写回什么 | 库建好了但接不进工作 |
| `采用记录.md` | 人 | 每跑一次记一行 | 说不清到底有没有用上 |

**规则正文永远只有一份：`AGENTS.md`。** 其他 Agent 文件只做入口，不复制判断。
.kb-base.json` 文件名固定（脚本按这个名字找），字段不能少；可变的是里面记的角色目录名和 Agent 配置。

模板里的 `{{为谁}}`、`{{回路名}}`、`{{怎么算有用}}` 由建库对话按任务书填；交付时 `AGENTS.md` 里不许留 `{{`。

## 三、六个角色 = 六个接口

| 角色 id | 默认目录 | 必有文件 | frontmatter `type` | 谁能写 |
|---|---|---|---|---|
| `inbox` | `00-Inbox` | 无 | — | 本人、所有入口动作 |
| `projects` | `01-Projects` | `<项目>/项目.md` | `project_status` | `project-ops`、本人 |
| `areas` | `02-Areas` | `<方向>/方向.md`、`记录规范.md`、`成长.md` | `direction` / `record_spec` / `review` | `area-review`、本人 |
| `knowledge` | `03-Knowledge` | 卡片、主题页 | `knowledge_card` / `theme_map` | `knowledge-card`、`theme-map`、本人签署 |
| `archive` | `04-Archive` | 无 | — | 收件、体检 |
| `me` | `05-Me` | `我是谁.md`（或等价一份） | `identity` | `me-update`、本人 |

规则：

1. **目录名可变，角色 id 不可变。** 他叫 `01-收件` 也行，`.kb-base.json` 里记 `"inbox": "01-收件"` 就行；
2. **角色缺了就不装依赖它的模块，`.kb-base.json` 里也不留这条映射。** 没有 `areas`，不写 `areas`，也不装 `area-review`；目录后来建了，再加回映射；
3. **一个角色只有一个目录。** 出现第二个入口，体检直接判堵塞。

## 四、读协议（Agent 开工先读什么）

任何 Agent 进这个库干活，按这个顺序读，读到够用为止：

```text
1. AGENTS.md            规则正文（Claude Code 先读 CLAUDE.md，它导入 AGENTS.md）
2. 05-Me/我是谁.md      我是谁、按什么标准交付
3. 工作回路.md          这次是哪条回路、读什么、产出什么、写回什么
4. 写入规则.md          东西从哪进、什么算处理完
5. 分区职责表.md        每类东西放哪
6. 任务相关的那一层      项目页 / 方向页 / 卡片 / 数据仓 schema
7. .kb-base.json        只在跑脚本、装模块、升级时读
```

**不许跳过 1 和 2 直接干。** 跳过 1 会越界写；跳过 2 会写出不像他的东西；跳过 3 会做成和本职工作无关的整理。

## 五、写协议

| 动作 | 谁能做 | 边界 |
|---|---|---|
| 起草 | 任何模块 | 先进候选区 / 进度文件，不直接进正式区 |
| 签署 | 本人 | 本人改一个字也算签署；AI 不能代签 |
| 覆盖 | 本人确认后 | 先列清单，再改；改完留 diff 或备份 |
| 删除 | 本人逐条确认 | 永不静默删；删除项先列清单 |
| 迁移 | 本人确认后 | 盘点 → 冻结 → 建新 → 搬 → 留退路 |
| 回路跑完 | 执行者 | 至少写回一样；并在 `采用记录.md` 记一行 |

**写回必须落文件。** 只在对话里说“已经记下了”，不算写回。

## 六、模块接口

模块登记在 `modules/manifest.json`。模块正文是 `modules/<名字>/SKILL.template.md`（模板不是可发现入口，装的时候才变成 `SKILL.md` 或清单）。新增一个模块只需要：

1. `modules/<名字>/SKILL.template.md`：写清边界、步骤、产出、验收、下一步（只建议）、失败时；
2. 在 `modules/manifest.json` 加一条：`name`、`version`、`role`、`default`、`requires`、`writes`、`placeholders`；
3. 占位符只用契约里这几个：`{{INBOX}}` `{{PROJECTS}}` `{{AREAS}}` `{{KNOWLEDGE}}` `{{ARCHIVE}}` `{{ME}}` `{{DATA_ROOT}}` `{{ROOT}}` `{{SKILL_ROOT}}` `{{DATE}}`；
4. 装完跑 `check_kb.py`，残留 `{{` 判失败。

**两种装法**：

| 模式 | 适合 | 装到 |
|---|---|---|
| `skills` | Claude Code / Codex | `.claude/skills/` 或 `skills/`，每个模块一个 `SKILL.md` |
| `checklists` | WorkBuddy / 通用聊天 | `操作模块/<模块>.md`，用户把文件发给 Agent |

**模块不许做的事**：改基座结构、改别的层的正文、自动调用下一个模块、把判断写进数据仓。

## 七、Agent 接口

| Agent | 规则文件 | 模块模式 |
|---|---|---|
| Claude Code | `CLAUDE.md`（导入 `AGENTS.md`） | `skills` |
| Codex | `AGENTS.md` | `skills` |
| WorkBuddy | `AGENTS.md` + `开场卡.md` | `checklists` |
| 通用网页 / App | `AI协作规则.md` + `开场卡.md` | `checklists` |

完整做法见 `Agent适配.md`。**装不了模块，不等于基座不能用。**

## 八、版本与升级

两个版本号，别混：

| 版本 | 管什么 | 什么时候加 |
|---|---|---|
| 基座版本 `version` | 这包文件发了第几版 | 任何文件改动 |
| 契约版本 `contract` | 角色 / 根文件 / 接口有没有破坏性变化 | 只在接口变了时加 |

规则：

- `contract` 不变：老库直接装新模块，不用迁移；
- `contract` 加一：老库要升级，**只加不改**——补根文件、补缺失角色、补 `.kb-base.json` 字段，不搬存量；
- 升级前先读 `.kb-base.json`，知道它建在哪一版、装了什么；
- 升级只动基座层，不碰他的项目和卡片；
- **改基座版本时同步三处**：`SKILL.md` 的 `version`、`scripts/install_modules.py` 的 `BASE_VERSION`、`templates/kb-base.json` 的 `version`。

当前：基座 `2.1.0`，契约 `2`。契约 2 相对 1 的变化：规则正文从 `CLAUDE.md` 改为 `AGENTS.md`；新增 `工作回路.md`、`采用记录.md`；`.kb-base.json` 新增 `agent`、`loops`；模块正文改为 `SKILL.template.md`，新增清单模式。

## 九、工作回路（用上的接口）

基座不保证「建了就会用」，所以把采用做成接口：`工作回路.md` 里每条回路写清 **触发 / 读什么 / 产出什么 / 写回什么 / 谁来做 / 算用上**；`采用记录.md` 每跑一次记一行。

- 建库当天必须跑第一条；
- 之后每次这件事真发生就跑，不按天数打卡；每跑 3 次看一次断点；
- 没跑起来，按 `工作回路.md` 的断点表查，不怪他懒。

## 十、私人来源（可选）

微信聊天、朋友圈不是新的角色，是**来源层**：

- 原文放 `私人来源/`（或独立私有仓），**不进 `03-Knowledge`**；
- 只提炼候选判断，来源指向原文；
- 接入前必须有 `私人来源清单.md`：来源、范围、同意人、脱敏项、保留期、删除日期；
- `.kb-base.json` 可选记录 `private_sources`；
- 体检：`03-Knowledge` 里出现聊天/朋友圈原文，判失败。

做法、适配器、同意流程见 `微信适配.md`。

## 十一、内容层怎么接

内容管线或第三方 skill 要接这个基座，只做五件事：

1. 跑脚本先读 `.kb-base.json` 拿角色目录和 Agent 配置，不写死目录名；
2. 开工读 `AGENTS.md`（或对应入口）和 `05-Me/我是谁.md`；
3. 先看 `工作回路.md`，知道这次服务哪条回路；
4. 写回只写自己那层：判断进 `knowledge` 的候选区，过程留项目，原文进来源，次数记采用记录；
5. 交接只建议下一步，不自动调用别的 skill。

**内容层不修改基座**。要改结构、改角色、换 Agent、加模块，回到 `knowledge-base-builder`。

## 十二、基座保证什么，不保证什么

**保证**：

- 东西有唯一去处，找得回来；
- 换一个 Agent、换一个模型，读 `AGENTS.md` 和 `05-Me` 就能接着干；
- 有一条可执行的工作回路，建库当天能跑出真产出；
- 模块可以换、可以卸，基座不动；
- 体检能看出结构缺什么、有没有真用上（`--profile base` / `use`）。

**不保证**：

- 保证不了他一定用——回路是不是真需求、节奏现不现实，要跑一周才知道；
- 保证不了判断都对——判断由他和证据决定；
- 保证不了自动整理——AI 只提案，签署和删除都要人点头。
