# 收件分流

> 入口只进不出，库就会死。这个 skill 只做一件事：每条东西给一个去向。

## 边界

- 不删原件，除非本人逐条确认；删除前先列清单。
- 不改写原文；只做去向判断和候选卡。
- 判断不了的放 `{{INBOX}}/_待判/`，不硬分。
- 分完的原件跟着去向走：进项目的放项目或来源区，进知识候选的原文放 `{{ARCHIVE}}/` 或来源区；分不清就留在 `{{INBOX}}/`，标「已处理，原件待定」。

## 步骤

1. **读规则**：先看根目录 `写入规则.md`，没有就按默认：项目 / 领域 / 知识 / 来源 / 归档。
2. **逐条过**，每条只问一个问题，从上往下，第一个“是”就停：
   - 它帮哪个正在做的事？→ `{{PROJECTS}}`
   - 它服务哪个长期方向（方向/标准/复盘）？→ `{{AREAS}}`
   - 它是可复用的判断/方法？→ `{{KNOWLEDGE}}/_候选/`
   - 它是别人的材料？→ 来源区或独立数据仓
   - 都不是 → `{{ARCHIVE}}`
3. **同一批里同类的合并**，不要一条一个文件。
4. **值得留的判断**先起草一张最小候选卡：一句话判断 + 来源 + `status: seed`。四要素的完整卡和签署交给 `knowledge-card`，收件这一步不越界。
5. **删除项单独列一张清单**，等他确认；不确认就留着。
6. **写回**：更新 `建库进度.md`，固定一行：处理 N 条 / 候选卡 M 张 / 归档 K 件 / 删除建议 J 条 / 入口剩 X 条。

## 产出

- 一张分流清单：每条 → 去向 → 理由
- 0–N 张候选卡
- 一份删除建议清单（未执行）

## 验收

- 每条都有去向，没有“其他 / 暂时放着”；
- 删除项一条都没动；
- 候选卡能追到来源。

## 下一步（只建议，不执行）

**停在这里。** 下面只是建议，操作者明确说做才继续。

- 如果分出了可沉淀的内容，可以问操作者要不要用 `knowledge-card`；
- 如果分出了有截止的事，可以问要不要用 `project-ops`；
- 如果是一批外部数据，可以问要不要用 `data-warehouse`；
- 操作者不说做，就停在这里。

## 失败时

- 分不下去 → 放 `_待判/`，记下为什么；
- 他嫌麻烦 → 先只处理最上面 10 条，跑通再继续。
