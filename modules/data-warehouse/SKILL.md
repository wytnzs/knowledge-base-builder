# 外部数据结构化入库

> 外部数据不是搬进来，是压成能查的结构；结构记下来，下次照着长。

## 三条原则

1. **原文不动**：原始文件留在来源仓，库里只存结构化记录 + 原文路径。
2. **按习惯设计**：字段由“他会怎么查”决定，不由“数据里有什么”决定。
3. **结构记住**：`{{DATA_ROOT}}/_schema/schema.json` 是唯一结构定义；下次入库先读它，不临时加字段。

## 什么时候用

- 手上有一批表格、PDF、网页、系统导出，想变成能查的库；
- 同一类数据反复手工整理；
- 想建判例库、产品库、客户库、资料库。

## 步骤

1. **盘数据**：来源、格式、大概多少、多久更新一次、有没有隐私。
2. **定实体**：一条记录是什么？一个判例、一个产品、一个客户，还是一份资料？
3. **问习惯**（决定字段）：
   - 你以后会怎么找它？按什么筛？
   - 哪些字段你从来不看？
   - 多久查一次、谁会查？
4. **设计压缩结构**：
   - 主键：自然键（案号 / 产品名 / 客户编号）或自增；
   - 字段：只留会被查、会被用的；长文压成摘要 + 原文路径；
   - 枚举统一（拒赔理由、客户阶段、产品类型）；
   - 每张表都加 `source_path`、`updated_at`。
5. **选存储**：
   - 经常筛选、统计 → SQLite 单文件；
   - 只是少量翻看 → Markdown 表；
   - 要和人交换 → CSV。
6. **建库 + 入库**：用本模块的 `scripts/init_warehouse.py`；先跑 20 条样本，验收后再全量。
7. **记住结构**：写 `_schema/schema.json` 和 `数据字典.md`；结构变了升 `version`，写变更日志。
8. **验收**：随机抽 5 条，按他的习惯查法能查到；每条能回到原文。

## 产出

- `{{DATA_ROOT}}/data.db`（或表文件）
- `{{DATA_ROOT}}/_schema/schema.json`
- `{{DATA_ROOT}}/数据字典.md`
- 一份入库日志

## 验收

- 同一类新数据第二次入库，不用重新设计；
- 随机查询能命中；
- 每条能追到原文；
- `schema.json` 与实际表一致。

## 失败时

- 字段太多 → 砍到“会被查”的，其他放原文；
- 数据不规整 → 先清洗 20 条样本，定规则再全量；
- 他改主意 → 升 schema 版本、写迁移，不悄悄改。
